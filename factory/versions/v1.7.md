# Factory V1.7

Date: 2026-11-27

## The need

Job #15 took 65 minutes and about $8, and opened no PR. An audit of its event log found four causes, and a review that cost more than the work it checked.

- **The factory changed under the running job.** Another session was building an uncommitted factory version in the main checkout during the job. The hooks run the main checkout's CLI and the job state lives there, so the judge changed mid-job. That version wrote a `lane` key into `job.json` that the worktree's CLI rejected: the user edited `job.json` with `sed`, ran a CLI command themselves and added a broad permission rule to go on. And when the job had to be abandoned, `factory clean --abandon` died on a `ZodError` for the same file: the user couldn't abandon the job they most needed to.
- **Every subagent's final hand-back was denied.** 54 denials of `SubagentHandback`, 3 to 8 per agent as it finished: `unjudged` denied any tool outside `SUBAGENT_TOOLS`.
- **Docker Desktop wasn't running.** `bun run services` failed and a red was rejected because e2e couldn't run; about 13 minutes passed before anyone noticed.
- **`curl -s -o /dev/null …` was denied** as "Write outside the job's worktree and folder: /dev/null".
- **The user talked to the CLI, not the orchestrator.** A Decision Request ended the orchestrator's turn, and the user had to run `! bun run factory answer <n> "<text>"` and then `/factory <n>` again; `clean`, `--abandon` and `watch` were the same.
- **The review ran everything again.** Pass 2 changed 4 files since pass 1: `apps/web/src/main.tsx`, exactly the file pass 1's finding 1 cited (`main.tsx:23`), and 3 test files. `planRoles` still planned a full blind review for both reviewers because a non-test file changed. In that pass the test reviewer ran 9 `sandbox exec` commands, 6 of them mutations, each a full build plus Playwright. In pass 1 the evaluator spent 4 of its 5 sandbox commands re-running checks `factory check` had already passed at that HEAD.

## What it changes

The definition is in [`factory/README.md`](../README.md), [`docs/isolation.md`](../docs/isolation.md), [`docs/operating.md`](../docs/operating.md), [`docs/quality.md`](../docs/quality.md) and [`factory-invariants.md`](../../knowledge/standards/factory-invariants.md).

- **The factory is frozen while a job is active (FI-026, FI-027).**
  - *Prevent:* while any job is `building` or `blocked`, the guard denies every Claude Code session of the repo, bound to a job or not, a write to the files that define how a job runs in the main checkout (`FACTORY_FILES` in `paths.ts`) and any git command that moves the main checkout's HEAD or working tree. The denial names the active jobs and says to work in a worktree or wait for the PR or the clean. Sessions bound to no job get no other verdict, and an error in this check never denies them.
  - *Detect:* `factory start` records a content hash of those files, uncommitted changes included; every CLI command on the job and every guard verdict of its session compares and refuses on a mismatch, naming the files. A resumed job with no record gets one.
  - `factory refreeze <n>`, user-only, accepts the new files. Not in the brief, added on my own: without it a legitimate `git pull` after another job's PR merged would strand every other job with no way out but abandoning it.
  - `mainRoot()` finds the main checkout from a worktree outside `.claude/worktrees/` through git's common directory.
- **The CLI brings Docker up (FI-029).** `factory start` and `factory check` begin with `docker info`; on a Mac with Docker Desktop installed they run `open -a Docker` and poll for about 90 seconds; elsewhere and in CI they only check; a Docker that isn't there refuses with what to do. The commands and the timeout are injectable.
- **`SubagentHandback` is allowed to every agent.** Its content is not judged: the text always reached the orchestrator as the agent's last message, a reviewer can't quote sealed material it can't read, and judging it would put back the denial loop the audit found.
- **`/dev/null` is no write** for any program; other `/dev/*` paths are judged as before.
- **The user talks to the orchestrator (FI-028).**
  - After `factory block` the orchestrator calls `AskUserQuestion`: the request's question, one option per Alternative, its recommendation first; the user can always write their own answer. A synchronous `PostToolUse` hook (`hook answer`, in `settings.json`) records the reply into the job state and the event log with the same "one answer authorizes one commit" meaning, and the orchestrator resumes in the same session with `factory start`.
  - The guard denies an `AskUserQuestion` call whose input carries `answers` or `annotations`. `factory answer` stays as the user's fallback and is still denied to the model.
  - `clean` and `clean --abandon` run only after a yes the user gave to a question the CLI wrote: `factory confirm <n> clean|abandon` logs and prints it, the orchestrator passes it to `AskUserQuestion` unchanged, the hook logs `confirmation.recorded` (or `declined`), the guard lets one `clean` through per yes and logs `confirmation.used`. The CLI words the question so the model can't reword what the user approves.
  - `factory start` starts `watch` in the background and opens the page in the user's browser; the token goes to `open`, never to the orchestrator's output. A running server is reused.
  - `factory clean <n> --abandon` works on a job whose `job.json` doesn't parse: it needs the job number and its folder, takes the worktree and branch from what is readable or from the checkout, runs each step on its own and says what it removed and what it couldn't. Plain `clean` and every other command still validate strictly.
- **Review in proportion to risk (FI-030, FI-031).**
  - A pass after the first is a `verify` when every non-test file changed since the previous pass is named in that pass's merged findings and the risk didn't rise; the evaluator verifies a product fix and carries its approval only past a change of tests.
  - Reviewers cite the `factory check` log as their evidence for the suite and run only targeted commands; the guard denies a whole-suite run inside `sandbox exec` (`turbo run lint typecheck test build`, `bun run test|lint|typecheck|build|e2e` at the root without `--cwd` or `--filter`). Written in both reviewers' instructions.
  - Each reviewer run has a budget of `sandbox exec` commands fixed by task and risk (`SANDBOX_BUDGET` in `review-plan.ts`; the plan prints each reviewer's number), counted per run from the event log, denied past it with "write your report with the evidence you have and list what you could not check as a finding". A ruling has none. Each command is killed after 5 minutes (injectable).
  - Mutation checks, the test reviewer's, come out of the same budget: none at low risk, at most 2 at normal, as needed at high.

## Validation

- `bun run lint`, `bun run format:check`, `bun run typecheck` and every `factory/cli` test (`bun run --cwd factory/cli test`) pass.
- New acceptance tests, each naming its invariant: `commands/freeze.acceptance.test.ts` (FI-026, FI-027), `commands/answer-channel.acceptance.test.ts` (FI-028), `docker.acceptance.test.ts` (FI-029), `commands/review-budget.acceptance.test.ts` (FI-030, FI-031, with job #15's pass 2 planned as `verify`).
- Technical tests with their value records: `/dev/null` and `SubagentHandback` (`commands/hook-handback.test.ts`), `mainRoot` on a real worktree outside `.claude/worktrees/` (`job.test.ts`), the background live page (`watch/background.test.ts`), `start` refusing before it touches anything when Docker is down (`commands/start.test.ts`), and `abandon` on three kinds of unreadable `job.json` (`commands/lifecycle.test.ts`).
- Not run: a real job under the new guard, a real `AskUserQuestion` through the hook, and a real Docker Desktop start. The first two depend on Claude Code's behavior (see what was learned).

## What was learned

- **What `PostToolUse` gets for `AskUserQuestion`.** Checked in the transcripts of earlier sessions on this machine, only for that tool's result: the user's reply is the record `toolUseResult` of the tool result, an object with `questions` (the input's questions), `answers` (an object from each question's full text to the label the user chose, or the text they typed) and `annotations` (an object, empty when the user added no note; per-question `notes` otherwise). A dismissed question is an error result with a short string. The hook reads `tool_response.answers` and falls back to `tool_input.answers`. This is the transcript's shape, not an observed hook payload: the hook input's `tool_response` is the tool's own result, which is what `toolUseResult` records, but a live run is still to confirm it.
- **`$CLAUDE_PROJECT_DIR` in another worktree** is that worktree's own root (where the session started), so its hooks run the worktree's copy of the CLI and `settings.json`. Job state is in the main checkout either way, and `mainRoot()` finds it. A worktree cut before this version doesn't carry the freeze until it is rebased.
- **Job state's unknown keys don't fail a load here.** `Job` is a non-strict `z.object`, so a `lane` key is stripped on load; job #15's failure was the other direction, a CLI that rejected what a newer one wrote. The abandon test therefore uses wrong types and non-JSON, which do fail.
- **The factory under change, FI-022, is a different problem.** The freeze keeps the main checkout still while a job runs; a job whose own PR changes the factory and is judged by its own edited copy is still the lane's to solve.
- **A review's cost sat in what it re-ran.** Two full blind reviews over a fix named in the findings, mutation runs of the whole build, and re-running a green suite were the cost; the plan, the evidence rule and the budget each cut one.
