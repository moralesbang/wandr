# Factory V1.6

Date: 2026-11-27

## The need

The orchestrator is the boss of a job, and the user is the boss of the orchestrator. V1.3 put the orchestrator on Sonnet at medium effort to save cost, but nothing made it so: a skill's frontmatter `model` applies only to the turn that loads the skill, and a sentence in the skill's body can't change the session's model. In job #15 the orchestrator's `usage` events (those with no `agent`) show about 6 to 14 messages on `claude-sonnet-5-5` and about 47 on `claude-opus-5-5`, the model the user's own session ran. The model of the agent that writes the classification proposal the route comes from, merges the reviewers' findings and decides when to raise a Decision Request was left to whatever the session happened to run. FI-019 had the same hole one level down: the orchestrator copied what `factory launch` printed into its Agent call, and nothing denied a call that carried something else; `factory watch` showed the drift after the fact.


Job #15 also showed the launch gap from the other side: four `general-purpose` subagents on Sonnet ran in a job whose agents are meant to launch only a Haiku `Explore`. One was a test reviewer's own launch, which its `Agent(Explore)` allowlist didn't stop; three were the orchestrator session's, unrelated to the job. The guard had no rule on subagent types (see what was learned).

## What it changes

The definition is in [`factory/README.md`](../README.md) and [`docs/isolation.md`](../docs/isolation.md).

- **The orchestrator runs Opus at high effort.** `ORCHESTRATOR` in `launch.ts`, the skill's frontmatter and its body, the `factory watch` page's expectation for the orchestrator and the tests that stated the old setting all change. Judgment is the orchestrator's whole job, so it gets the judging model.
- **The guard enforces the orchestrator's setting.** On every call the main session makes inside a job, the guard reads the model and effort of the latest assistant message in the session's transcript (`transcript_path` in the hook input) and denies the call unless they are `ORCHESTRATOR`. The reason tells the user to run `/model opus` and `/effort high` and retry. A transcript it can't read, or that shows no model, is denied (the guard's fail-closed rule). `factory status` stays allowed, and the user's own `!` commands fire no hook, so the user is never locked out. Subagents are not judged by it: the transcript is the main session's.
- **The guard enforces every launch's setting, by plan.** `factory launch` gives each plan an id and prints a `header` line, `factory-launch: <n> <agent> <task> <plan id>`; the Agent call's prompt starts with it. The Agent tool has no task parameter, so the header is what makes the task deterministic: matching by agent alone let a test reviewer's `ruling` plan (Opus, low) authorize a `review` launch at the same setting. The guard denies the call when the header is missing or malformed, the plan id is unknown, belongs to another job or was used, or the call's agent, task, model or effort differ from the plan's (a missing model or effort is a difference). When it lets a launch through it logs `launch.authorized` with the plan id, which uses the plan up: one plan authorizes one launch, a stale plan can't authorize a later run, and a denied call uses none. The same call judged again (same tool use id) is the launch already authorized.
- **A factory agent launches only Explore, on Haiku (FI-024).** The guard denies every Agent or Task call from a subagent of a job unless its type is `Explore` and its model is `haiku`. See what was learned for why the model is required, not defaulted.
- **Inside a job the orchestrator launches only factory agents with a plan, and Explore on Haiku (FI-025).** `general-purpose` and every other type is denied. "Inside a job" is what the guard already means by it: the session is the `session` of a job whose `job.json` exists, in any state (`building`, `blocked`, `pr_open`), until `factory clean` removes the job. Nothing about the job's lifecycle changes.
- **FI-019 covers both,** with the guard in its mechanism, and adds FI-024 and FI-025; `commands/hook-orchestrator.acceptance.test.ts` defends all three. The guard fixture gives every test an Opus-at-high transcript and, by default, plans and fills in the orchestrator's factory launches, so a test about another rule isn't judged on the plan; `launches: 'strict'` turns that off.

## Validation

- `bun run lint`, `bun run format:check`, `bun run typecheck` and every `factory/cli` test (`bun run --cwd factory/cli test`: 2026 tests) pass.
- The new acceptance tests drive the hook from the session's input to the verdict: wrong model, wrong effort, an unreadable transcript, the status command, the latest message deciding, a launch with no plan, with a wrong or missing model or effort, a plan used up, a newer plan replacing an older one, another agent's plan, and Explore calls by the orchestrator and by subagents.
- The tests added for the plan header cover the ruling-plan-used-for-review case, a used plan, a plan of another job, and every type the orchestrator and the agents may not launch; FI-025's test runs in `building`, `blocked` and `pr_open`.
- A real job run with the new guard is still pending.

## What was learned

- **The transcript carries what the session ran.** Each assistant line has `message.model` (`claude-opus-5-5`) and a top-level `effort`; the Agent tool's `model` parameter uses short names (`opus`). In job #15's session transcript every assistant line had both fields.
- **The current message is already in the transcript when PreToolUse fires.** Checked on job #15, not by a live hook run: the assistant line holding the Agent call for the first fix round is stamped 21:03:39.097Z and the `agent.prompt` event the hook logged for the same call 21:03:39.189Z, about 90 ms later, for the first call. The guard reads the latest assistant message that is in the file, so if a Claude Code version wrote it later, the check would judge the message before and be one message late, never blind.
- **Four `general-purpose` runs in job #15 were two different things.** The first, at 20:48, was the test reviewer's own choice: its transcript shows an `Agent` call with `subagent_type: general-purpose`, `model: sonnet`, to run mutation checks, although its `tools` say `Agent(Explore)` and its instructions say to hand code search to a Haiku `Explore`. Nothing stopped it: the `Agent(Explore)` allowlist doesn't constrain a subagent here, and the guard's agent-prompt policy lets every subagent type through when an agent made the call (`promptPolicy` returns allow). It wasn't a code search, so the instruction didn't cover it either; the run's sandbox command was denied, since only a reviewer has a sandbox. The other three, at 21:15, were the orchestrator session's: the main session was reused after the job for the user's own follow-up work and launched three `general-purpose` runs on `sonnet` with `isolation: worktree` (the factory fixes "Make factory check hermetic", "Make factory review proportional" and "Add factory fast lane for UX"), unrelated to issue #15. The guard has no rule on non-factory subagent types, from the orchestrator or a subagent. FI-024 and FI-025 close both: the reviewer's call is denied as a factory agent's launch of a non-Explore type, and the orchestrator's three as launches of a non-factory type. Job #15 had no PR (its `job.json` still says `building`), so those three came mid-job, not after one; its session was bound to the job, which is why the hook logged their `agent.prompt` events in the job's log, so the rule would have denied all three.
- **Explore's default model is not known here, so Haiku is required, not defaulted.** No transcript on this machine shows an Explore launched without a `model`: every one of the 30 found passed it, 29 of them `sonnet` and one `haiku`, despite the agents' instructions to use `haiku`. The Agent tool's description lists no default model for Explore. So the guard requires `model: "haiku"` and denies an omitted model and any other.
