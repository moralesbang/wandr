# Factory V1.3

Date: 2026-11-27

## The need

Job #13 (issue #13, PR #19, cost $5.69) ran end to end on V1.2 and opened its PR, and the run showed ten problems in the factory itself:

1. **The blind pass wasn't blind.** Both reviewers read the Decision Request, which repeats the build notes, before their blind pass in round 1, and the earlier final reports and findings in round 2. They read through `Bash` (`cat`), and `factory watch` flagged nothing because it classified only `Read`.
2. **A Decision Request's authorization wasn't recorded.** It was posted on the issue, where any `gh` call from a tool call looked like the user's own comment, and nothing tied the next acceptance-test commit to an answer.
3. **The reviewers shared the end-to-end stack.** Port 3100, `apps/web/dist` and the test database were common: the evaluator read a manifest the test reviewer had broken on purpose, and took it for the build.
4. **Round 2 re-reviewed everything.** A one-file acceptance-test change reran both full blind reviews.
5. **The test agent was weak.** Its tests broke on lint, formatted wrongly, or failed on a broken helper rather than the missing feature, and it left AC clauses without an assertion.
6. **Model and effort weren't fixed.** The orchestrator chose them per run, so the same job could cost very different amounts.
7. **A test fix had two paths.** The orchestrator decided whether a fix kept the guarantee (`atfix`) or changed it (`rewrite`), so the orchestrator that merged the findings also judged whether a test's guarantee changed.
8. **There was no cost per agent.** The $5.69 was known only by adding up transcripts by hand.
9. **There was no risk level.** A copy change and a change to the privacy boundary got the same two Opus reviewers.
10. **The build delivered changes that didn't work.** Experiments, workarounds that proved unneeded and config tweaks stayed in the diff.

## What V1.3 changes

The definition is in [`factory/README.md`](../README.md).

1. **The blind pass is blind, by construction and by guard.** `factory review` plans a pass and seals it: the build notes, Decision Requests, diagnosis, summary and every earlier report move out of the worktree into the main checkout's state folder, where no command an agent runs reaches them. `factory unseal` brings them back only once each sealed reviewer's own run wrote its blind pass with the Write tool after the seal, and freezes each pass by its hash; `factory pr` checks the hash. The guard denies the same names as a second layer, and denies every subagent the main checkout, Claude Code's transcripts, file history and task outputs, and `gh`. `factory watch` now classifies the paths `Bash`, `Grep` and `Glob` read and flags denials; replaying job #13's commands flags the four early reads. `factory gate` rejects a commit message body, a merge commit and any git note: each would carry the build agent's reasoning past the seal in `git log`. It also refuses a branch that lost a commit the CLI made (the red commit, an acceptance-test fix): the CLI records each one's patch id, so a rebase onto `main` keeps them and a `git reset --hard <base>` doesn't.
2. **Only the user answers a Decision Request, and the answer is recorded.** `factory block` keeps the request in the job's folder and prints it for the orchestrator's terminal; nothing is posted on the issue. The user answers with `! bun run factory answer <n> "<text>"`. `factory start` refuses a blocked job until the latest request is answered. The next `rewrite`, or an `atfix` on a changed-guarantee request, cites the answer in its commit and uses it up: one answer authorizes one commit. The guard denies every tool call that runs `factory answer`, writes to GitHub through `gh`, pushes, or writes the job's state in the main checkout; a blocked job refuses every command that would move it.
3. **Each reviewer has its own sandbox.** `factory sandbox <n> <role>` makes a disposable detached checkout of `HEAD` inside the job's folder with its own dependencies, port, database and bucket; `sandbox exec` runs a command there with that environment, and `sandbox rm` removes it. Playwright reads `E2E_PORT` and never reuses a server when it is set. A reviewer writes anywhere in its own sandbox and nowhere in the other's, and outside `sandbox exec` runs an allowlist of read-only commands (everything else goes through `exec`, where the guard judges only the inner command from the sandbox); `clean` and `clean --abandon` remove both. An integration test runs two concurrent Playwright runs with different mutations, each seeing only its own.
4. **A review pass is sized to what changed.** `factory review` gives every reviewer the risk needs a full blind `review` on the first pass or after product code changed. After a change to tests alone, the test reviewer `verify`s the previous findings against `git diff <since> <head>` and the evaluator's approval is `carry`ed, or it `verify`s too when it hadn't approved. A verifier reads only the previous findings and its own previous report.
5. **The test agent runs what it writes.** Before it finishes it formats and lints every file, runs its tests and reads each failure, runs each helper against a valid sample, and maps every clause of every AC to an assertion in `acceptance.md`.
6. **Model and effort are fixed in the CLI.** `LAUNCH_TABLE` in `launch.ts` holds a model and effort per agent, task and risk. The orchestrator runs `factory launch <n> <agent> --task <task>` before every Agent call and copies the result into the call's `model` and `effort`. The orchestrator itself runs on Sonnet at medium effort, and the skill's body restates it.
7. **A test fix has one path.** The test agent leaves the fix uncommitted; `factory ruling` hashes it; a fresh test reviewer rules `same-guarantee` or `changed-guarantee` in a file naming that hash. `factory atfix --ruling <m>` commits a same-guarantee fix only when the hash matches and the log shows the reviewer's own run wrote the ruling. A changed guarantee is a Decision Request, and the user's answer authorizes the fix as ruled or a `rewrite`.
8. **Cost per agent.** The `SubagentStop` and `Stop` hooks read each run's transcript, deduplicate by message ID and log one usage event: tokens by kind, models, efforts and the cost from a dated price table. `factory watch` shows each run and the job's total, and the PR comment opens with a per-agent table. On job #13's transcripts it gives $5.69.
9. **A risk level.** The issue form has a required Risk field (`low`, `normal`, `high`). The effective risk raises `low` to `normal` when the diff touches the privacy boundary or a tamper-prone file; it never lowers a risk or raises one past `normal`. At low risk there is no evaluator, and the model and effort of the reviewers follow the level.
10. **The build delivers only what worked.** The build agent reverts every change that had no effect on the result before it finishes.

The live page grew with them. `factory watch` shows the job's risk and what raised it, each pass's review plan, the seal and unseal, the rulings, each run's cost and the job's total, and a model or effort that drifts from what `launch` planned. The event log gained the events behind them: `usage` per run, the denials of every guarded tool, and the CLI's review, seal, ruling and answer steps.

The guard grew with these. It now matches every tool (`*`), judges every call a job makes, fails closed on any error inside a job, and judges real paths with symlinks resolved. A subagent uses only the tools the guard can judge, and the orchestrator has no MCP tool during a job. `watch` serves its page and stream only to a request carrying a token it makes at start.

### The adversarial review

Before closing the version the guard went through three rounds of adversarial review, each hunting for ways past it:

- **Round 1** found 18 holes.
- **Round 2** found about 14 more.
- **Round 3** was the final verification of the fixes. It found these, all fixed with an end-to-end test that drives the hook (or the CLI function) with the verifier's own input and was red before the fix:
  - **`--` after the script hid the subcommand.** Bun drops a `--` that follows the script (and `bun run factory` drops one more), so `bun run factory -- --note x answer 7 yes` reached the CLI as `answer` while the guard read `--note` as the command. The guard now reads the call as `main.ts` receives it, and no `--` hides the subcommand.
  - **Shells.** Only `sh -c`, `bash -c` and `zsh -c` were read. Now every shell (`bash`, `sh`, `zsh`, `dash`, `ksh`, `mksh`, `fish`, `busybox sh`, behind `env` or a launcher) is read through any flag cluster with a `c` (`-lc`, `-ec`, `-e -c`, `--norc -c`), and `eval`'s literal arguments are read as a command. A shell fed code on stdin (`| bash`, `bash <<<`, `bash <<EOF`, `bash -s`) is denied.
  - **The CLI's commits could leave the branch.** A build agent's `git reset --hard <base>` dropped the red commit and its acceptance tests, and the gate, which skipped the CLI's commits, passed the rebuilt branch. The gate now requires each CLI commit to be in the branch, by commit or by patch id, and the guard denies the build, test and diagnose agents the reset, `rebase --onto` and amend that would drop one. The patch id is also what lets the instructed `git rebase main` pass.
  - **The other reviewer's sandbox through walks.** `rg`, `grep -r`, `find` or a glob rooted in `factory/.jobs/<n>/sandbox`, and interpreter operands under `sandbox exec`, read it. A walk or glob that reaches the other sandbox is denied, as is one from at or above the sandboxes for any other subagent; `rg` and `grep` from the worktree root skip the gitignored job folder and stay allowed.
  - **A pending verifier's sealed names, and the other reviewer's blind pass.** A nested run under a verifier read the build notes while no seal stood, and a reviewer read the other's blind pass before writing its own. Both are denied.
  - **A reviewer's runner denylist.** It listed `bun test` and a few others and let `curl`, `psql`, `node`, `ps` and any script through. A reviewer outside `sandbox exec` now runs an allowlist of read-only commands.
  - **`git credential`** handed out the user's stored GitHub token; it and `git credential-*` are denied to everyone.
  - **A reviewer's own sandbox was not its own.** Under `sandbox exec` the guard judged the outer command from the worktree, so `-- git reset --hard`, `git stash` and `git checkout -- .` were denied in the sandbox made for them. Only the inner command is judged, from the sandbox.
  - **Writes of protected paths past `>` and `tee`:** `rsync`, `ditto`, `exec N>`, `ed`, `ex`, `vi -es`, `awk` redirections, `git rm`, `git mv`, `git checkout <rev> -- <paths>`, `git restore --source`, `tar x`, `unzip`, `patch`, `curl -o`, `wget -O`, `chmod`, `rm` and `find -delete`, and any of them on a folder holding a protected path. The factory README lists what stays uncovered; the gate sees every commit.
  - **The text and the guard disagreed.** The build agent's file said `git notes`, `git config`, `update-ref`, `branch -f` and a merge were denied; the guard denied them only to the reviewers. The guard now matches the text: `git notes`, `update-ref`, `tag`, `branch -f` and `-d`, `git config` writes and a merge are denied to every agent, and the orchestrator can't write a note.

The holes were of a few kinds: a guard that failed open on an error or an unknown tool; symlinks that led a path somewhere its text didn't say; launchers (`env`, `nice`, `sh -c`, `xargs`) and interpreter operands (`bun -e`, `node -e`) that hid a command from the parse; forged verdicts (a reviewer's report or ruling written by the orchestrator, a forged hook event, a blind pass written by an `echo` from another run); a session rebound by `factory start --session`; merges, notes and amended-away message bodies that hid changes or reasoning from the gate; and a command the guard read in one place and the runtime read in another (`--`, flag clusters). Every fix has an end-to-end test that drives the hook from the session's input to the verdict, run against the code before the fix.

## What was learned

- **A per-launch Agent `effort` parameter works.** It is undocumented; the subagent's transcript recorded the effort it was given. The orchestrator therefore sets model and effort per run from the CLI, and the agents' frontmatter is a default.
- **A user-typed `!` command fires no `PreToolUse` hook, and a model's Bash call does,** with the same environment and no TTY. `factory answer` can't tell the two apart, so the guard is what separates the user from the model.
- **A skill's frontmatter model and effort apply only to the turn that loads it.** The skill's body restates the orchestrator's model and effort for every later turn.
- **Transcripts carry `effort` and the usage of each assistant message,** which is what makes the per-agent cost exact.
- **`~/.claude/file-history` keeps copies of files the orchestrator wrote,** and the transcripts and task outputs hold the build agent's reasoning too. The guard closes all of them to subagents.
- **A text-parsing Bash guard can't be complete.** Each review round found spellings the previous one missed. The guard stops the plain cases and the careless agent; the residual (a script written then run, code built at runtime) needs OS-level sandboxing of Bash, planned next. Meanwhile the gate, `unseal`, `atfix` and `pr` check the event log and the commit history instead of trusting the guard.
- **A reviewer is independent by what it can reach, not by what its prompt says.** Moving the sealed files out of the worktree beat every denial rule written about them.

## Open risks

Only the next real `/factory` run confirms these:

- **The orchestrator's model and effort holding across turns.** The body restates them; whether the session stays on them is unobserved. `factory watch` shows a drift from the planned model or effort.
- **The real savings.** Against #13's $5.69, the estimate is about $2.90 at low risk and about $3.70 at normal.
- **The sandbox flow in a real review, and seal and unseal in a live run.** Both are tested end to end, but no real reviewer has used them yet.
- **The hook's latency.** About 60 ms on every tool call, from a Bun process per call.
- **The factory's end-to-end tests add about 20 s to the checks.**
- **`removeSandboxes` needs the services up** to drop a sandbox's database and bucket; `clean` fails without them.
- **The gate's trailer allowlist may reject `BREAKING CHANGE`** in a build commit, which Conventional Commits puts in a footer.
- **A seal stuck on a missing blind pass has no `--force`.** The reviewer is relaunched; if it can't write its blind pass, the user is told.
- **The Bash policy's false positives.** A harmless command that looks like a denied one is refused, and the agent must find another way.
- **Background task output is denied to subagents.** They run long commands in the foreground or redirect output into a file.
- **A nested `Explore` can't be tied to its parent,** so it is judged as any subagent, not as the reviewer that launched it.
- **Reviewers share the services by name only (G4).** The other reviewer's database and bucket are denied by name in a command, but both live in one Postgres and one MinIO, so a reviewer that finds another route reaches them; inside `sandbox exec` a `pkill`, `ps` or `kill` reaches the other reviewer's processes. A role-scoped database user is the fix, and OS-level sandboxing for the processes.
- **The guard is keyed on the session id (G8).** `factory start --session` rebinds the job to a new session, and in the window before that call the new session's tool calls are unguarded. Only the skill's step order covers it: `start` is the first command of a run.
- **The gate's patch id can change when `main` changes the context lines around a CLI commit's hunk.** A rebase over such a change makes the gate say the commit is gone; the message gives the `git cherry-pick <sha>` that restores it. The red commit adds new files, so the usual case is stable.
- **The reviewer allowlist refuses what a reviewer used to run outside the sandbox:** `curl` to its server, `psql`, `ps`. They go through `sandbox exec`, where the same command works with the reviewer's own environment.
- **A worker's `find` from the worktree root is denied once a reviewer made a sandbox,** since it walks `factory/.jobs/`; `rg`, `grep` and the Grep and Glob tools from the root, and `find apps`, stay.
- **Expiring the reflogs doesn't collect the amended-away object.** No ref names a rejected commit body any more, but the object stays until git's own `gc`.
