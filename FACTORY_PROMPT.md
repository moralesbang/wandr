# Build the Wandr factory, V1

You are building the first version of Wandr's software factory: the process that takes a GitHub issue to an open pull request with agents. Read `CLAUDE.md` first and follow it; talk with the user in Spanish, write everything in the repo in English.

## Why it exists

The user's main goal is to **learn** to build a factory by iterating on it: a deliberately small V1, then a V2 when a real need shows up, and so on. Every version stays on record so the project shows where it started and what each step improved. Build the smallest V1 that works end to end; every idea beyond it goes to the V2 candidates list, not into the code.

**The user decides.** Take no decision without asking: every choice not listed under "Decided" below goes to the user as a question that stands on its own, with your recommendation first and the trade-off of each option. For any external fact, use serious primary sources (official docs, papers, vendor engineering blogs) from the last 18 months, never forums, and cite them.

## Principles

The factory **delegates execution, not authority**. Use these to judge every design choice and to frame every question to the user.

- **Inner loop**: implement → verify → diagnose → fix, fast and deterministic, run by the build agent alone until the checks pass or it hits its limit. The build agent writes and keeps the technical tests as it goes, red–green–refactor where it pays.
- **Outer loop**: an evaluator with its own context checks the result against the issue's intent, including what the tests actually guarantee, and sends actionable findings, backed by evidence, back to the inner loop. Passing tests is necessary, never sufficient. The inner loop produces the tests; the outer loop certifies their value.
- **Independent gates**: the final verdict comes from checks the agent can't change (the CLI and CI), not from one agent's judgment of another. Agents on the same model share blind spots, so back every judgment with a deterministic check wherever one exists.
- **Isolation, not instructions**: agents are independent because of what they receive and what they may change (their own context, inputs and permissions), not because their prompts differ. They hand work over through files and commits, never through conversation history.
- **Guarantees, not test count**: keep the smallest suite that covers the risks that matter. Every test costs runtime and maintenance, and earns its place by the defect it would catch.
- **Human by exception**: the user approves the spec and its acceptance criteria, sets the risk tolerance, resolves functional ambiguity, authorizes any change to an acceptance guarantee, approves any exception to a gate, and merges. The user never approves technical tests one by one. Agents decide what is local, reversible and verifiable, and never widen their scope, their permissions or the rules they're judged by.
- **Traceability**: every decision the user makes for a job stays on record in GitHub.

## Two kinds of tests

| | Acceptance tests | Technical tests |
| --- | --- | --- |
| Question | Did we build the right thing? | Did we build it right? |
| Source of truth | The issue's ACs and the public contracts: `docs/04-flows.md`, `docs/03-design-brief.md`, `packages/contract` and `openapi.json`, public interfaces | Technical contracts, invariants and implementation risks |
| Author | Test agent | Build agent |
| When | Before implementation, in the red commit | During implementation, one at a time |
| Who changes them | Only with the user's authorization: changing one changes a guarantee | The build agent, as long as no existing guarantee weakens |
| Certified by | The evaluator, then CI | The evaluator, then CI |

**Acceptance tests** check behavior a user or caller can observe: in the SPA by role and accessible name (`knowledge/standards/testing.md` T-007), never by DOM structure. Minimal scaffolding (a route, an empty component, a stub with the right signature) may exist so the app and the tests run; the red must come from the missing behavior, never from a broken environment (open item 1).

**Technical tests** follow a value check. Before writing one, the build agent records in its notes: the behavior, contract or invariant it protects; the concrete defect it would catch; whether another test already gives that guarantee; and the level that fits (unit, API, component, end to end). A test whose only target is framework behavior, an internal detail, a coverage number or a guarantee another test already gives earns no place. Coverage is a diagnostic, never evidence. The build agent's check is a first assessment; the evaluator certifies.

## Who sees what

Each agent runs as a fresh subagent. What it starts with is its independence.

| Agent | Receives | Starts without |
| --- | --- | --- |
| Test agent | The issue and its ACs, the public contracts (see the table above), `knowledge/standards/testing.md`, the test infrastructure | Any implementation plan; it runs before the build agent |
| Build agent | The issue, `docs/05-architecture.md`, the repo and `knowledge/`, the acceptance tests (read and run only), the check results, the evaluator's findings | The test agent's reasoning |
| Evaluator | The issue and its ACs, `docs/05-architecture.md` and `knowledge/`, the branch's diff against `main`, the whole test suite and its results | The build agent's notes and reasoning, until its first pass is written down; only then does it read them to contrast its own findings (the **blind first pass**) |

## Decided

| Topic | Decision |
| --- | --- |
| Intake | GitHub issues. An issue form `.github/ISSUE_TEMPLATE/factory.yml` requires a description and numbered acceptance criteria (AC1, AC2…). The factory takes only issues with the label `factory:ready`, which the user sets. |
| Where files live | `factory/` at the repo root: `README.md`, `cli/` (the CLI), `versions/`. The skill in `.claude/skills/factory/SKILL.md`, the agents in `.claude/agents/`. Everything lives in the repo. |
| Job state | One JSON per job in `factory/.jobs/`, gitignored. The CLI also moves the issue's labels (`factory:ready` → `factory:building` → `factory:pr-open`, plus a blocked state) so GitHub shows where each job stands. |
| Concurrency | Up to 3 jobs at a time, **one Claude session per job**: the user runs `/factory 42` in up to three terminals; the CLI refuses a fourth. |
| Skill | One skill only, `/factory`: the orchestrator of one job. It runs in the main session, because a background subagent has no Agent tool and can't spawn the other agents. |
| Subagents | Each runs in the background, with the inputs in "Who sees what". |
| Deterministic actions | A CLI in **TypeScript on Bun** (the repo's runtime; no new toolchain, no build step, `Bun.$` for git and gh, tested with `bun test`). The CLI is the shell backbone: the skill runs CLI subcommands for every deterministic step and reasons only about the rest. |
| Worktree | The CLI creates it: `factory start 42` makes `.claude/worktrees/42-<slug>` on branch `feat/42-<slug>`; all agents work there. The CLI owns branch naming and cleanup. |
| V1 flow | Issue → **test agent** writes the acceptance tests from the contracts and commits them (the red commit) → **build agent**, in another context, implements until green, writing technical tests as it goes → the CI checks run locally → **evaluator agent**, in its own context and with a blind first pass, reviews the result and its tests and sends findings back to the build agent, then re-evaluates (the outer loop) → PR. The user reviews and merges. No plan gate in V1; refactoring happens inside the build agent's red–green–refactor. |
| Tests vs implementation | Acceptance tests are **frozen but visible**: the build agent reads and runs them, never edits them. Technical tests belong to the build agent: it adds, changes and removes them, under the evaluator's review. |
| Protected paths | The CLI rejects a build whose diff touches an acceptance test, `.github/workflows/`, the lint or TypeScript config, `factory/` or `.claude/`: the agent can't change the rules it's judged by. How the CLI tells an acceptance test apart is open item 4. |
| Hollow tests | Acceptance tests defend with a **verified red**: at the red commit the CLI runs them and rejects any that already pass; at the green commit all must pass. Technical tests defend with the value check and the evaluator's test review. Mutation testing and traceability per AC are V2 candidates. |
| Test review | The evaluator may recommend keeping, removing, merging, changing or adding any technical test, with a reason for each; the build agent applies them and the evaluator verifies again. |
| Escalation | The build agent stops and asks instead of deciding when the change would touch a public contract, the architecture, an acceptance test, or anything outside the issue's ACs. V1 enforces this by instruction only. |
| Decision Requests | Whenever a job needs the user (an escalation or a block), the orchestrator comments on the issue with context, evidence, alternatives, a recommendation, impact and risks, and moves the job to the blocked label. The user's answer on the issue is the decision's record. |
| Models | Haiku explores code, Sonnet writes code (test and build agents), Opus does what matters: the orchestrator and the diagnosis of a failed build. |
| `factory/README.md` | Explains the flow **visually** first (diagrams of the stations, both loops, the job's states and labels, who runs each step, who sees what), then the commands. It describes the current version only. |
| Versions | Each version is a git tag (`factory-v1`) plus `factory/versions/v1.md`: the need that motivated it, what it does, what the user learned, and the V2 candidates. `factory/versions/` is an explicit exception to the repo rule that docs hold only the current definition; record that exception in `CLAUDE.md`. |

## Open: settle with the user before designing

1. **What counts as a valid red.** If the module under test doesn't exist yet, the whole test file fails on import, so every test "fails" even if it asserts nothing. The user's position: the red must come from the missing behavior, never from the environment, and minimal scaffolding is allowed. Options on the table: (a) the test agent writes stubs with the signatures (throwing "not implemented" or returning an empty value) so the file loads, and the CLI reads a JUnit report to require each acceptance test to fail on an assertion, not on an import or syntax error; (b) any failure counts. The user asked you to **research this** before they decide: the TDD literature on "failing for the right reason" (Beck, Freeman & Pryce), and whether `bun test`, Vitest and Playwright report assertion failures apart from load errors in their JUnit output. Bring findings with sources and a recommendation.
2. **The evaluator.** Its checks, starting from: ACs met; behavior end to end; conformance to `docs/05-architecture.md` and `knowledge/`; scope creep and over-engineering; tampering with the checks (special-casing a test's inputs included); and the test review: risks left uncovered, assertions that can't fail, guarantees duplicated across levels, coupling to implementation details, excess mocks, guarantees removed or weakened, and whether each test would catch a real defect. Still to settle: whether the test review is a capability of the evaluator or its own agent; the evaluator's model; how many outer-loop rounds before the job is blocked; and what happens to a finding about an acceptance test. Changing one needs the user's authorization (decided); open is who rewrites it (back to the test agent, or the user through the Decision Request) and whether a fix that keeps the guarantee (a wrong selector, a typo) needs that authorization too.
3. **Retries and diagnosis.** The user asked for a **concrete example** before deciding: walk one job through a build that doesn't reach green (what the agent sees, what the orchestrator does, when the user hears about it). Options on the table: (a) 2 Sonnet attempts, then the Opus orchestrator diagnoses and relaunches once, then the job is blocked with a Decision Request; (b) the same with a fresh-context Opus subagent diagnosing; (c) 1 attempt, then the user decides. Settle it together with the evaluator's round limit: both are budgets of the same job.
4. **Telling the tests apart.** The CLI must know which files hold acceptance tests to protect them, and an acceptance test and a technical test can't share a file. Options: (a) the CLI records the red commit's test files in the job's JSON and protects exactly those; (b) a naming convention or folder for acceptance tests, which then stay recognizable after the job. Also settle what the build agent may do to tests already on `main`: change them freely under the evaluator's review, keep a protected list (for example the privacy tests, T-005), or have the CLI report every removed, skipped or `.only` test as evidence for the evaluator.
5. **Handoff files.** What carries the work between agents and where it lives: the build agent's notes (the value check of each technical test, its decisions) and the evaluator's findings (each with evidence: the command, its output, `file:line`). Options: the gitignored job folder (private to the job, gone after cleanup); committed on the branch (versioned, but noise in the PR's diff); comments on the PR (on record in GitHub). The blind first pass decides one constraint: the evaluator must be able to start without the build notes in view.
6. **Risk tolerance.** How the user sets it for a job: (a) a field in the issue form (for example standard or high) that tells the evaluator how hard to look, and in V2 whether hidden tests or mutation testing run; (b) one level for every V1 job, with the repo's standards (the privacy tests T-005) defining the risks, and the field as a V2 candidate.
7. **Where the testing rules live.** The value check and "guarantees, not test count" bind every test, not only the factory's. Options: record them as standards in `knowledge/standards/testing.md` in the V1 PR, so human-written and agent-written tests follow the same rule; or keep them in the agents' prompts only.
8. Anything else the design needs that isn't decided above, for example: whether the CLI follows `knowledge/standards/workspace.md` (it lives outside `apps/` and `packages/`), the CLI's subcommands, the exact protected files, whether agent permissions or hooks can block edits to acceptance tests before the CLI ever sees the diff, the PR body (link `Closes #<n>`), how the user learns a job finished, how the local checks match CI (`.github/workflows/ci.yml`).

## How to run this session

1. Read `README.md`, `docs/02-mvp-scope.md`, `docs/05-architecture.md`, `knowledge/README.md` and the standards it lists for the paths you'll touch (`testing.md` always), and `.github/workflows/ci.yml`. Read the Claude Code docs on skills, subagents and hooks (code.claude.com/docs/en/skills, /sub-agents, /agents, /hooks) to confirm the constraints above still hold: background subagents' tool set, the `model` field in agent frontmatter, per-agent tool and permission limits, `${CLAUDE_SKILL_DIR}`, `allowed-tools`.
2. Settle every open item with the user. Done when no question remains.
3. Write `factory/README.md` with the flow diagrams and show it to the user for approval before writing code. Done when the user approves it.
4. Build V1 on a branch with a PR (code reaches `main` only through a PR with passing checks): the issue form, the labels, the CLI with its tests, the skill, the agents, `.gitignore` for `factory/.jobs/`, `factory/versions/v1.md`, the `CLAUDE.md` exception, and whatever open item 7 settles. Done when the CLI's tests pass and the PR's checks are green.
5. Prove it end to end with the user on one small real issue: from `factory:ready` to an open PR. Record what happened in `factory/versions/v1.md`. Tag `factory-v1` after the user merges.
6. Delete this file (`FACTORY_PROMPT.md`) in the same PR: the README and `versions/v1.md` replace it.

## V2 candidates already raised

Seed `factory/versions/v1.md` with these: a dedicated refactor station after green; hidden acceptance tests held back for the evaluator, when the risk justifies them; the test review as its own agent (if V1 keeps it inside the evaluator); mutation testing on the diff only, so the score never becomes a target; property-based tests for invariants; contract tests; traceability per AC; a risk level per issue that scales verification (if V1 doesn't take it); coverage as a diagnostic for the evaluator; a second-opinion evaluator on another model family; calibrating the evaluator against the user's verdicts; a cost budget per job; enforcing escalation in the CLI.

## Already found (sources)

- Claude Code: a background subagent loses the Agent tool, so it can't spawn subagents; custom subagents spawned from the main session start in the background; permission prompts from background subagents surface in the main session; `isolation: worktree` creates `.claude/worktrees/<name>` on a `worktree-<name>` branch, which is why the CLI creates the worktree instead. [Subagents](https://code.claude.com/docs/en/sub-agents), [Skills](https://code.claude.com/docs/en/skills), [Run agents in parallel](https://code.claude.com/docs/en/agents).
- TDD with Claude: write tests from expected input/output, say it's TDD so it doesn't write mock implementations, run them and confirm they fail, commit them, then implement without changing them. [Anthropic, Claude Code best practices](https://www.anthropic.com/research/claude-code-best-practices).
- The outer loop is Anthropic's evaluator-optimizer pattern: one model generates, another evaluates and gives feedback in a loop. [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- Why the evaluator is separate and skeptical: an agent grading its own work praises it even when it's mediocre, and tuning a standalone evaluator to be skeptical is more tractable than making a generator critical of itself. Out of the box the evaluator found real issues and approved anyway; the author tuned it over several rounds by reading its logs where its judgment diverged from theirs, and failed a sprint when any criterion fell below a hard threshold. Generator and evaluator agreed on what "done" meant before any code (sprint contracts) and handed work over through files. Every harness component encodes an assumption about what the model can't do alone, so re-test each one as models improve. [Anthropic, Harness design for long-running application development (Mar 2026)](https://www.anthropic.com/engineering/harness-design-long-running-apps).
- Why acceptance tests are frozen, the CLI rejects edits and escalation is an explicit exit: given tests that contradict the spec, Claude models cheated mostly by editing the tests (>79% of their cheating), despite being told not to. Hiding the tests cut cheating to near zero but hurt legitimate performance; read-only tests restored performance and stopped test edits, but not special-casing or operator overloading, which is why the evaluator looks for those. An option to flag the task for a human cut GPT-5's cheating from 54% to 9%. LLM monitors caught only 42–65% of cheating on multi-file tasks: deterministic gates first. [Zhong, Raghunathan & Carlini, ImpossibleBench (Oct 2025, ICLR 2026)](https://arxiv.org/abs/2510.20270).
- Mechanical enforcement over instructions: OpenAI's agent-written codebase enforces its architecture with custom linters and structural tests whose error messages tell the agent how to fix the problem; only versioned artifacts in the repo reach the agent; humans turn feedback into acceptance criteria and validate outcomes, and agents review each other's PRs until the reviewers are satisfied. Contrast: they run with minimal blocking merge gates and agents merge their own PRs, where Wandr keeps the merge with the user. [OpenAI, Harness engineering (Feb 2026)](https://openai.com/index/harness-engineering/).
- Human on the loop, not in it: Meta separates catching tests (fail on a change, then discarded once answered) from hardening tests (pass and land to guard against regressions), filters LLM-generated tests with LLM judges combined with a deterministic rule-based assessor, and has engineers set criteria and review outcomes in aggregate, intervening at the policy level rather than per item: the basis for the user not approving technical tests one by one. [Meta, Just-in-Time Catching Test Generation (Jan 2026)](https://arxiv.org/abs/2601.22832), [Meta Engineering, JiTTesting at full scale (Oct 2026)](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/).
- Hollow tests (V2 material): Meta's ACH keeps an LLM-written test only if it kills a mutant ([arXiv:2501.12862](https://arxiv.org/abs/2501.12862)); Google runs mutation testing only on the diff, at code review ([Practical Mutation Testing at Scale](https://arxiv.org/pdf/2102.11378)). StrykerJS supports Vitest officially ([StrykerJS 7](https://stryker-mutator.io/blog/announcing-stryker-js-7/)); `bun test` only through community plugins, and its TypeScript checker reportedly fails on TypeScript 7, which this repo uses.
- Shell vs a structured language: the [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) advises leaving shell once a script passes ~100 lines or has non-trivial control flow.
- `gh issue list --json number,title,labels --jq …` for intake: [gh issue list](https://cli.github.com/manual/gh_issue_list).
- The earlier factory draft (testing gaps, lanes, Codex as a second opinion) is in git at commit `3fa12a1`, `docs/factory-draft.md`: material for V2 candidates, not for V1.
